## 1. PROJECT OVERVIEW

**WedCrew** (`mywedcrew.com`) is a two-sided marketplace connecting wedding
**production companies** with **freelance crew** — cinematographers,
photographers, drone pilots, video editors.

**Problem solved:** production houses need to find, vet, book, message and pay
crew for specific events in specific cities on specific dates; freelancers need
discovery, a portfolio, availability control and earnings.

### User roles (exactly three, from `User.role` enum)
| Role | Enum value | Purpose |
|---|---|---|
| Company | `company` | Posts requirements, finds and books crew, pays |
| Freelancer | `freelancer` | Portfolio, applies to work, receives bookings and earnings |
| Admin | `admin` | Platform operations, master data, subscriptions, finance, moderation |

There is **no separate Company or Freelancer model** — both are `User`
documents distinguished by `role`. Do not create separate models.

### Architecture
```
React 19 SPA (Vite)  ──HTTP/JSON (axios)──►  Express REST API  ──►  MongoDB Atlas
        │                                          │                  (Mongoose)
        └────────Socket.IO (JWT handshake)─────────┘
```
- Frontend calls the backend at `VITE_API_URL`, defaulting to
  `http://<current-hostname>:5000` (see `frontend/src/utils/api.js`).
- Auth is **stateless JWT** in `localStorage`, attached by an axios request
  interceptor.
- Socket.IO shares the same JWT (handshake `auth.token`).

### Main business workflows
1. **Company → Freelancer:** booking request → freelancer accepts → *connected*
2. **Freelancer → Company:** company posts requirement → freelancer applies →
   company accepts → *connected*
3. Connection opens exactly **one Conversation**; chat additionally requires
   **both** parties to hold a plan granting the `chat` feature.
4. Payments (online/cash) may then flow company → freelancer, minus a platform fee.

## 6. AUTHENTICATION

**Files:** `backend/src/controllers/authController.js`,
`backend/src/middleware/authMiddleware.js`,
`backend/src/middleware/adminMiddleware.js`,
`backend/src/services/passwordPolicy.js`,
`frontend/src/context/AuthContext.jsx`,
`frontend/src/components/ProtectedRoute.jsx`,
`frontend/src/utils/api.js`.

- **Signup** `POST /api/auth/register` → bcrypt `genSalt(10)` + hash. Password
  policy (8+, upper, lower, number, special) enforced **on set, not on login**,
  so existing users are never locked out.
- **Login** `POST /api/auth/login` → `bcrypt.compare` → JWT signed with `JWT_SECRET`.
- **Token storage:** `localStorage['token']`; axios request interceptor adds
  `Authorization: Bearer <token>`. A 401 response clears the token.
- **Middleware:** `protect` (401 if absent/invalid), `optionalAuth` (attaches
  `req.user` when a valid token exists, otherwise continues anonymously),
  `admin` (403 unless `req.user.role === 'admin'`).
- **Socket auth:** JWT via handshake `auth.token` in `backend/src/socket.js`.
- **Frontend guard:** `ProtectedRoute` with `allowedRoles`; wrong role is
  redirected to that role's own dashboard.
- **Logout:** clears localStorage + context.
- **Password reset:** ❌ **NOT IMPLEMENTED** (no reset route, token, or email).
- **Token expiration:** **NEEDS VERIFICATION** — confirm `expiresIn` in
  `authController.js`; there is no refresh-token mechanism.

## 10. BOOKING SYSTEM (actual implemented flow)

**Two independent directions both lead to "connected":**

```
A) COMPANY-INITIATED
   Company POST /api/booking-requests  ──► BookingRequest{status:'pending'}
        │  (notification → freelancer: 'new_booking_request')
   Freelancer PUT /api/booking-requests/:id/status {status:'accepted'}
        ├─► ensureConversation()  → exactly one Conversation
        └─► notification → company: 'booking_request_accepted'
   ⇒ CONNECTED (via 'booking')

B) FREELANCER-INITIATED
   Company POST /api/requirements  (must be status:'published' to be applied to)
   Freelancer POST /api/applications  ──► Application{status:'pending'}
        │  (notification → company: 'new_application')
   Company PATCH /api/applications/:id/status {status:'accepted'}
        ├─► ensureConversation()  → reuses the SAME conversation if one exists
        └─► notification → freelancer: 'application_accepted'
   ⇒ CONNECTED (via 'application')
```

**Statuses:** BookingRequest `pending|accepted|declined`.
Application `pending|shortlisted|accepted|rejected`.

**Connection is DERIVED, not stored** (`services/connectionService.js`):
an accepted BookingRequest **OR** an accepted Application between the pair.
Pending/declined/rejected/shortlisted are *not* connected.

**Duplicate prevention (`canSendBookingRequest`):**
| Situation | Result |
|---|---|
| A pending request already exists | blocked `DUPLICATE_BOOKING_REQUEST` |
| Connected, **no** `requirement_id` | blocked `ALREADY_CONNECTED` (redundant — message instead) |
| Connected, **new** `requirement_id` | **allowed** — legitimate new work |
| Connected, same requirement already accepted | blocked as duplicate |

Duplicate applications are blocked by the DB unique index
`{requirement_id, freelancer_id}` — per requirement, so applying to a
*different* requirement of the same company is allowed.

**After acceptance:** conversation exists; chat still gated by subscription.
**After rejection/decline:** notification only; no connection, no conversation.

## 15. AVAILABILITY SYSTEM

**Two complementary models — do not merge them:**

| Model | Answers | Used by |
|---|---|---|
| `Availability` | "which individual days am I free" (single dates) | legacy day calendar |
| `AvailabilityBlock` | "where am I, between these dates, with what status" | travel/location-aware search |

`AvailabilityBlock` statuses: `available`, `booked`, `busy`, `traveling`,
`unavailable`. Only `available` is **bookable** (`BOOKABLE_STATUSES`).

**How "current Udaipur + future Jaipur shoot" works:**
The freelancer's **base location** is `User.city_id/state_id`. Separately they
create date-ranged blocks with their own `city_id`. Search
(`GET /api/public/freelancers`) matches **base OR travel**:
1. `base` — `user.city_id` matches the searched city
2. `travel` — an `AvailabilityBlock` with a bookable status in that city covers the date
3. `blocked` — a non-bookable block covering the date **excludes** the user (so a
   BOOKED freelancer never shows as free), *unless* they are travelling into the
   searched city with a bookable block

Base-location matches sort above travelling ones (`match_type`).
Overlap validation lives in `services/availabilityService.js`.
API: `GET/POST /api/availability/blocks`, `PUT/DELETE /api/availability/blocks/:id`.

## 16. PORTFOLIO / GALLERY

**Backend:** `models/GalleryItem.js`, `controllers/galleryController.js`,
`controllers/admin/galleryController.js`, `services/mediaEmbedService.js`,
`services/uploadService.js`.
**Frontend:** `components/gallery/{PortfolioManager,GalleryGrid,MediaModal}.jsx`,
`utils/mediaEmbed.js`.

**Supported sources:** uploaded image, uploaded video, YouTube, Instagram, Vimeo.

**Security (`mediaEmbedService.js`) — this is the boundary:**
1. https only (`javascript:`, `data:`, http all rejected)
2. Host **allow-list** per platform
3. Strict ID character classes (YouTube 11 chars, Vimeo digits, Instagram 5–30)
4. **The embed URL is REBUILT from the extracted ID** — the user's original
   string is never echoed into an iframe

Playback is **in-site**: YouTube → `youtube-nocookie.com/embed/<id>`,
Instagram → official `/embed/` (**not** `/embed/captioned/` — the caption block
forced a nested scrollbar; legacy rows are normalised on read by
`normaliseEmbedUrl`, without a migration), Vimeo → `player.vimeo.com`,
uploads → native `<video>`.

**MediaModal:** iframe/video mounted **only when opened** (a 40-item gallery
costs 40 thumbnails and zero players), `scrolling="no"`, sandboxed, ESC to close,
body scroll lock, 8s timeout → "Unable to play this video here" + platform link.
Instagram gets a portrait reel viewer sized to `56px header + 4:5 media`
(measured constants `IG_HEADER_PX`, `IG_MEDIA_RATIO`, `IG_MAX_WIDTH` in
`MediaModal.jsx`) so Instagram's own footer is clipped rather than scrolled.

**Uploads:** multer memory → `uploadService.store()`; extension comes from a MIME
allow-list table (never the client filename), random filenames, per-user
directories. Served read-only from `/uploads` with `nosniff`, CSP sandbox,
non-GET → 405. Limits: images 8 MB, videos 100 MB.

**Admin moderation:** `is_hidden` (reversible) + hard delete; hidden items are
excluded from public responses by the query itself.

**Social links:** validated per-platform host allow-list; **public URLs only, no
credentials are ever requested or stored.**

## 18. CURRENT PAYMENT SYSTEM — **IMPLEMENTED** (recently added)

> an automated suite (72/72)** but has **never run against live Razorpay keys**.

### IMPLEMENTED / VERIFIED
| Area | Detail |
|---|---|
| Money handling | **Integer paise everywhere.** `services/money.js`. `fee + net === gross` exactly, verified |
| Platform fee | Configurable in `FinanceSetting.fee_bps` (basis points). **Not hardcoded** |
| Ledger | `LedgerEntry`, append-only; schema hooks refuse update/delete; **balances derived, never stored** |

| Webhooks | Raw-body mount **before `express.json()`**, HMAC verified, idempotent via unique `(provider, event_id)` |
| Idempotency | `Idempotency-Key` header → unique partial index; replay returns the original payment |
| Admin finance | Overview, transactions, withdrawals, disputes, settings, ledger adjustments |
| Audit + notifications | Reuses the **existing** ActivityLog and Notification systems |

**Payment statuses (16):**

`REFUND_REQUESTED`, `REFUND_PROCESSING`, `REFUNDED`, `REFUND_FAILED`.
Cash — `CASH_PENDING`, `CASH_CONFIRMED`, `CASH_DISPUTED`, `CASH_CANCELLED`,
`CASH_REFUND_REQUESTED`, `CASH_REFUND_CONFIRMED`.

**Ledger types (10):** `DEPOSIT`, `BOOKING_PAYMENT`, `PLATFORM_FEE`,

## 27. IMPORTANT BUSINESS RULES

1. **Chat requires BOTH parties** to hold a plan with the `chat` feature
   (`canChat`). One-sided subscription is not enough.
2. **Chat messages never create a Notification.** Unread chat is a separate badge.
3. **Connection is derived**, never stored: accepted BookingRequest OR accepted
   Application.
4. **Exactly one Conversation per (company, freelancer) pair**, whichever
   direction connected them — always via `ensureConversation()`.
5. **Duplicate booking requests blocked when connected**, *unless* scoped to a
   new `requirement_id` (genuine new work is always allowed).
6. **One application per requirement per freelancer** (DB unique index).
7. **Public profiles are allow-listed**, never deny-listed. Email, phone and
   coordinates can never leak.
8. **Without a subscription the professional's identity is withheld server-side** —
   name, photo, bio, equipment, social links and gallery are never serialised.
9. **Requirements default to `draft`**; only `published` ones accept applications.
10. **Availability:** only `available` blocks are bookable; a non-bookable block
    excludes the freelancer from date-filtered search.
11. **Money is integer paise.** Never use floats. `fee + net === gross` must hold.
12. **Ledger entries are immutable** — corrections are new ADJUSTMENT/REVERSAL rows.
13. **Balances are derived from the ledger**, never stored on a user.
14. **Payments only between connected parties.**
15. **`FAILED` payments can never become `SUCCESS`** — a retry is a new payment.
16. **Webhooks are the authoritative payment confirmation**, not the browser.
17. **Withdrawal debits on request** (not completion) so concurrent requests
    cannot overdraw; failure posts a REVERSAL.
18. **Payout identifiers are `select:false`**; only `masked` is ever returned.
19. **Activity logging must never break a business operation** — `logActivity`
    never throws, and metadata is allow-listed.
20. **Never log or store:** passwords, JWTs, API secrets, full bank/UPI
    identifiers, private emails/phones, message bodies.
21. **Legacy data is never destroyed** — unmatched master-data values are flagged
    `needs_master_review`, not deleted.

## 30. SAFE DEVELOPMENT RULES

1. **Inspect existing code before changing anything.**
2. Preserve existing functionality; the site is in production use.
3. Do not rebuild existing systems unnecessarily.
4. Do not modify unrelated features.
5. Reuse existing components/services — especially the authority services (§3).
6. Follow the existing architecture (controller → service → model).
7. Do not delete functionality without explicit instruction.
8. Do not change database structure unnecessarily.
9. **Do not reset MongoDB.** Real user data exists.
10. **Do not overwrite `.env`.** Edit `.env.example` instead.
11. Never expose or log secrets.
12. Run the E2E suites after changes (§24) — **509 assertions is the baseline**.
13. Run `npm run build` in `frontend/` after any frontend change.
14. Verify the backend starts (`npm start`) after any backend change.
15. Perform regression testing across all nine suites, not just the one you touched.
16. Make minimal changes.
17. **If something conflicts with a requested feature, explain the conflict first**
    rather than making a destructive change.

### Extra practical notes learned the hard way
- **`lucide-react@1.31` has no brand icons** — the build fails on `Instagram`,
  `Youtube`, `Facebook`, `Linkedin`.
- **oxlint baseline is 30 warnings.** Above 30 = your regression.
- **E2E suites delete ALL `@e2e.local` users** on cleanup — if you seed data for
  manual UI testing with that suffix, another suite will remove it.
- Suite cleanup can leave **orphaned rows** (e.g. gallery items whose owner was
  deleted). Check for and remove orphans, but **only where the owner no longer exists**.
- The dev machine's system DNS resolver (`127.0.0.1`) has been observed
  **refusing SRV queries**, which breaks `mongodb+srv://`. If the backend cannot
  connect but general internet works, that is the cause — not the app code.
  Public DNS (8.8.8.8) resolves it correctly.
